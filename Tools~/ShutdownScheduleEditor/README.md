# ShutdownScheduleEditor

StreamingAssets의 `ShutdownSettings.json`(요일별 기본 종료 스케줄 + 특정 날짜 재정의)을 편집하는
독립 실행형 Windows GUI 도구. Unity가 설치되어 있지 않은 전시 현장 PC에서도 사용할 수 있도록
Unity 패키지(Runtime/Editor asmdef)와는 완전히 분리된 .NET WinForms 프로젝트로 둠.

종료 스케줄은 `Settings.json`과 섞지 않고 별도 파일로 분리해, 현장에서 스케줄만 따로 수정해도
다른 설정 파일을 건드릴 일이 없도록 함.

## 데이터 구조

`Runtime/Data/TemplateData.cs`의 `ShutdownSetting`/`ShutdownDaySchedule`/`ShutdownDateOverride`와
동일한 스키마를 사용하며, `ShutdownSetting`이 파일의 루트 오브젝트임.

```json
{
  "monday":    { "enabled": true,  "time": "21:30" },
  "tuesday":   { "enabled": true,  "time": "21:30" },
  "wednesday": { "enabled": true,  "time": "21:30" },
  "thursday":  { "enabled": true,  "time": "21:30" },
  "friday":    { "enabled": true,  "time": "22:00" },
  "saturday":  { "enabled": false, "time": "22:00" },
  "sunday":    { "enabled": false, "time": "22:00" },
  "dateOverrides": [
    { "date": "2026-12-25", "enabled": false, "time": "" }
  ],
  "shutdownArguments": "-s -f -t 45"
}
```

`dateOverrides`에 등록된 날짜는 같은 날짜의 요일별 기본 스케줄보다 우선 적용됨(실제 우선순위
판정 로직은 이 스키마를 소비하는 런타임 매니저 쪽에서 구현).

## 사용법

**파일 > 프로젝트에서 열기(Ctrl+P)** 로 Unity 프로젝트 루트 폴더(Assets가 있는 폴더) 또는
StreamingAssets 폴더를 선택하면 `StreamingAssets/ShutdownSettings.json`을 자동으로 찾아 엶.
파일이 없으면 확인 후 기본값(모든 요일 비활성, 월 09:10·그 외 17:35, 특정 날짜 없음)으로 새로 생성함.

정확한 파일 경로를 알고 있으면 **파일 > ShutdownSettings.json 파일 직접 열기(Ctrl+O)** 를 사용.

편집 후 **저장 (Ctrl+S)** 버튼 또는 **Ctrl+S** 로 저장. 제목 표시줄의 `*` 는 저장하지 않은 변경이 있다는 뜻. 창 하단의 **작업 스케줄러 갱신** 버튼을 누르면 현재 스케줄을 작업 스케줄러 백업에 즉시 반영하며(미등록 시 등록 창 연결), **작업 스케줄러 삭제** 버튼으로 등록된 백업 작업을 손쉽게 제거할 수 있음.

### 요일별 기본 스케줄

요일마다 `종료함` 체크와 시각을 지정함. 체크를 끄면 그 요일에는 종료하지 않음.

### 특정 날짜

기본적으로 비어 있으며, 등록된 날짜는 **그 날의 요일별 기본 스케줄 대신** 이 설정이 적용됨
(예: 월요일은 21:30 종료지만 특정 월요일 하루만 종료하지 않게 하거나 시각을 늦출 수 있음).

날짜 · 종료 여부 · 시각을 위쪽 입력 줄에서 고르고 `날짜 추가` 를 누르면 목록에 등록됨.
같은 날짜를 다시 추가하면 덮어쓸지 확인함(한 날짜에 설정이 두 개 생기지 않도록).
잘못된 형식이 들어갈 여지를 없애려고 목록은 직접 편집할 수 없으며, 수정하려면
`선택한 날짜 삭제` 후 다시 추가할 것.

### 종료 명령 인수

종료 시각에 실행할 Windows `shutdown` 명령의 인수. 기본값은 `-s -f -t 45`.

| 인수 | 뜻 |
|---|---|
| `-s` | 종료 (재부팅은 `-r`) |
| `-f` | 실행 중인 앱 강제 종료 |
| `-t <초>` | 지연 시간 |

지연 시간을 두는 이유는 종료 로그 전송이 끝날 시간을 확보하기 위함. 비워둔 채로는 저장되지
않으며, `기본값` 버튼으로 언제든 되돌릴 수 있음.

## 런타임 연동

이 파일을 실제로 읽어 종료를 실행하는 쪽은 `Runtime/Core/ShutdownScheduler.cs`.
씬에 배치하면 `RootLifetimeScope.ConfigureOptionalComponents`가 자동 등록함(다른 선택 매니저와
동일한 `RegisterIfPresentInScene` 패턴이라 배치하지 않으면 조용히 비활성).

동작 순서는 다음과 같음:

1. 시작 시 `ShutdownSettings.json`을 로드하고, 주기적으로(기본 15초) 예정 시각 도달 여부 확인
2. 도달하면 `OnBeforeShutdown` 이벤트 실행(페이드아웃 등 프로젝트별 마무리를 연결)
3. `shutdownArguments`로 `shutdown` 실행 — 지연 시간(`-t`)만큼 OS 종료가 예약됨
4. `Application.Quit()`으로 앱을 정상 종료

종료 로그는 이 매니저가 직접 보내지 않고 `ApiManagerBase`의 종료 로그 경로가 담당함(아래 참고).
예약 종료든 사용자의 수동 종료든 종료 경로를 하나로 모아야 예약 종료 때만 로그가 두 번
기록되는 일이 없기 때문. 3번에서 예약한 지연 시간이 로그를 마저 보낼 여유가 됨.

예정 시각이 이미 지난 뒤에 앱을 실행하면(운영자가 밤에 재시작한 경우 등) 그날은 건너뜀 —
켜자마자 다시 꺼지는 것을 막기 위함.

## 작업 스케줄러 백업 (도구 > 작업 스케줄러 백업)

유니티 앱이 멈춰서 스스로 PC를 끄지 못하는 경우를 대비한 안전망. 예정 시각 +N분(기본 5분)에
Windows 작업 스케줄러가 PC를 대신 끔. 유니티와 무관한 별도 프로세스로 실행되므로 유니티가
프리징·크래시 상태여도 동작함.

### 왜 가드 스크립트를 거치는가

작업 스케줄러의 트리거는 "요일 + 시각" 반복은 표현할 수 있지만 **"특정 날짜는 제외"를 표현할
수 없음.** 요일 트리거만 걸면 휴무일로 지정한 날에도 백업이 PC를 꺼버림.

그래서 트리거는 시각을 잡는 역할만 하고, 실제 종료 여부는 작업이 실행되는 순간
`ShutdownBackupGuard.ps1`(등록 시 설정 파일 옆에 자동 생성)이 `ShutdownSettings.json`을 다시
읽어 판단함:

1. 오늘 날짜가 특정 날짜 목록에 있으면 그 설정을, 없으면 요일 설정을 사용
2. `종료함`이 아니면 아무것도 하지 않고 종료
3. 예정 시각 + 지연 시간이 아직 안 됐으면 아무것도 하지 않고 종료
4. 위를 모두 통과하면, 같은 폴더의 `Settings.json`에서 `apiUrl`을 읽어
   `"end_kill (by Task Scheduler)"` 종료 로그를 직접 전송(전송 실패는 무시하고 계속 진행)
5. `shutdownArguments`로 `shutdown` 실행

이 경로가 발동한다는 것 자체가 유니티(및 `ApiManagerBase`의 정상 종료 로그)가 응답하지 못했다는
뜻이므로, 정상 종료 로그("end")와 구분되는 "end_kill" 값으로 별도 전송함. 유니티 프로세스와
무관한 PowerShell 프로세스라 유니티가 멈춘 상태에서도 전송을 시도할 수 있음.

실행 기록은 설정 파일 옆 `ShutdownBackup.log`에 남음.

### 스케줄을 수정했을 때 재등록이 필요한가

가드가 실행 시점에 파일을 다시 읽으므로 **잘못 꺼지는 방향의 변경은 재등록 없이 반영**되지만,
새로 켜거나 시각을 바꾸는 변경은 트리거 자체가 옛날 값이거나 아예 없어 **백업이 조용히 동작하지
않게 됨.**

| 변경 | 재등록 |
|---|---|
| 특정 날짜를 휴무로 추가 | 불필요 (트리거는 떠도 가드가 건너뜀) |
| 요일 끄기 | 불필요 (동일) |
| 요일별 시각 변경 | **필요** |
| 요일 켜기 | **필요** |
| 특정 날짜를 종료함으로 추가 | **필요** (그 날짜의 트리거가 없음) |
| 특정 날짜의 시각 변경 | **필요** |

이 상태를 눈치채지 못하는 것이 가장 위험하므로, 백업이 등록된 상태에서 저장하면 확인창 없이
곧바로 함께 갱신함(기존에 쓰던 지연 시간 그대로 유지). 확인창 자체가 깜빡하고 지나치기 쉬운
지점이라, "저장 = 백업도 최신 상태"라는 규칙 하나만 기억하면 되도록 함.

### 등록되는 작업

작업 이름은 `shutdown-backup`이며, 다음 설정으로 등록됨:

| 설정 | 값 | 이유 |
|---|---|---|
| 사용자의 로그온 여부에 관계없이 실행 | O (`S4U`) | 자동 로그인이 풀려 있어도 백업이 동작해야 함 |
| 암호를 저장하지 않습니다 (로컬 리소스만 접근) | O | S4U에 포함. 로컬에서 `shutdown`만 실행하므로 제약이 되지 않음 |
| 가장 높은 수준의 권한으로 실행 | O (`HighestAvailable`) | 종료 실행과 로그 기록이 권한 때문에 막히지 않도록 |
| 놓친 작업 따라잡기(`StartWhenAvailable`) | X | 켜면 아침에 켠 키오스크를 그대로 다시 끔 |

**등록·해제에는 관리자 권한이 필요함.** S4U와 최고 권한 실행은 승격 없이 등록되지 않으므로,
`등록 / 갱신`과 `등록 해제`를 누르면 UAC 창이 뜸(취소하면 안내 후 아무 변경 없이 종료).
상태 조회는 읽기 전용이라 승격 없이 동작함.

### 제약

- 종료 시각 + 지연 시간이 자정을 넘기면 트리거가 다음 날로 밀려 가드가 엉뚱한 요일을 보게
  되므로, 등록 시 막고 안내함
- UAC 승격은 출력 리디렉션을 지원하지 않아, 등록 실패 시 종료 코드만 표시되고 schtasks의
  상세 메시지는 나오지 않음

## 빌드 및 실행

.NET 8 SDK 이상 필요.

```bash
dotnet build
dotnet run
```

파일 경로를 인자로 주면 실행과 동시에 해당 파일을 열어줌.

```bash
dotnet run -- "C:\path\to\StreamingAssets\ShutdownSettings.json"
```

## 배포 (현장 PC에 .NET 런타임이 없는 경우)

전시 현장 PC에 .NET 8 런타임이 설치되어 있지 않을 수 있으므로, 단일 실행 파일로
self-contained 게시를 권장함.

```bash
dotnet publish -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true
```

`bin/Release/net8.0-windows/win-x64/publish/ShutdownScheduleEditor.exe` 하나만 복사해서
현장 PC에서 실행하면 됨(네이티브 DLL도 exe 안에 묶여 있어 다른 파일 없이 이거 하나로 동작함).

### StreamingAssets에 넣어두고 바로 실행하기

이 exe를 프로젝트의 `Assets/StreamingAssets/` 폴더에 두면, 인자 없이 실행해도(더블클릭) **같은 폴더의 ShutdownSettings.json을 자동으로 찾아 엶**. 파일이 아직 없더라도 기본값으로 자동 생성해 바로 열어주므로, 매번 "프로젝트에서 열기"로 경로를 찾을 필요 없이 StreamingAssets 폴더에서 이 exe를 실행하기만 하면 됨.

이 방식으로 두면 프로젝트를 빌드할 때 exe가 StreamingAssets 전체와 함께 최종 빌드에도
그대로 포함되어, 현장에 배포된 빌드 폴더 안에서 편집기가 항상 설정 파일 옆에 붙어 있게 됨.
단, exe 코드를 수정한 뒤에는 `dotnet publish`로 다시 게시해서 수동으로 교체해야 함(자동
갱신되지 않음).
